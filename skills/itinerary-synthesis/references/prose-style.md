# 行程文字的判斷題

`itinerary.yaml` 的 `title`、`checklist[]`、`contingency[]`、`days[].label`、
`days[].rows[].text` 會被四種 renderer 原樣搬給讀者看。`no_ai_tone` 已經機械擋掉
破折號、粗體、裝飾性 emoji 和 AI 套語，那些不用在這裡重講。這份文件只處理擋不掉的
三件事，它們都得你自己判斷。

## 一、三項並列：能不能拆掉一項

`no_ai_tone` 不查三項並列，因為行程裡的並列多半是真的：`清水地熱、望龍埤、外澳沙灘`
是三個地名，`小卷米粉、活龍蝦、卯澳海景海鮮` 是三道菜。這種列舉照寫，數量由事實決定。

要警惕的是另一種：三個項目不是清單，而是你把一句話硬拆成對仗的三段，好讓它看起來完整。
「交通便利、環境舒適、服務貼心」就是這種，三項都沒有資訊，拿掉任何一項讀者都不會損失
什麼。判斷方式：逐項問「刪掉它，讀者會不會少知道一件可以照著做的事？」全部答不出來，
整組刪掉，改寫成那一件真正要說的事。

同一個判斷也適用四字標籤。`交通便利` 這種現場造出來的四字詞在行程裡幾乎一定可以換成
具體數字（`飯店走到車站 5 分鐘`）。標籤是空的，標籤後面那句才是內容。

## 二、節奏：連續同構的 row 要打斷

一天的 rows 是垂直讀下來的，所以同構特別刺眼。連續五行都是
`地名，形容詞短語、形容詞短語、形容詞短語` 的時候，讀者會停止閱讀、開始掃描，而他掃不到
自己要的那個時間或那個電話，因為每一行長得一樣。

處理方式不是把句子改漂亮，是讓長度隨資訊量走：只需要交代「在哪吃」的 row 就寫短
（`午餐：和平火雞肉飯`），帶著限制條件的 row 本來就會長（`低消每人 150、收客 20:00，
假日不接受訂位，建議 18:00 前到`）。長短交錯是資訊分佈的自然結果，不是刻意變化。

`checklist` 同理。它是出發前逐條核對的東西，每條應該是一個可以打勾的動作，不是一段
說明。一條裡塞三個動作，就是三條。

## 三、具體 vs 空泛：這一行有沒有可以照著做的東西

這是最重要的一條，也是唯一真正影響行程可用性的一條。

上游的 `verified-pois.yaml`、`calendar.yaml`、`transit.yaml` 已經幫你把事實查好了。
寫 row text 的時候，優先搬事實，而不是搬感受：

| 空泛 | 具體 |
|---|---|
| 這裡風景很美，值得一訪 | 180 度正對龜山島，室內有冷氣 |
| 建議提早前往，避免人潮 | 週日不接受訂位、現場候位，18:00 前到 |
| 交通方便 | 車站走路 5 分鐘 |
| 記得注意天氣 | 出發前 3 天查中央氣象署颱風／豪大雨特報 |
| 這家店很有名 | Google 4.4，近 7 千則評論 |

「值得一訪」「風景優美」這類詞的問題不是它們有 AI 味，是它們**佔掉了本來可以寫事實的
位置**。這一站已經被排進行程了，你不需要再說服讀者它值得去；讀者要的是到了現場用得上的
東西，幾點關、要不要預約、有沒有冷氣、停車怎麼辦。

例外：使用者自己指定的東西照他的話寫。`這是你指定必訪的一站` 是在回覆使用者的要求，
不是在推銷景點，該保留。

寫完一個 row，問一句：這行字，讀者在現場能拿它做什麼？答不出來就重寫。
